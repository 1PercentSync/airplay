# 研究笔记 04：音频捕获调研（阶段二）

> 证据标记同前。Sunshine 参考：`reference/repos/Sunshine` @ cf52f4b6。

## 1. Q4：Sunshine 捕获链路实际行为（代码级）

| 环节 | 事实 | 证据 |
|---|---|---|
| API | WASAPI 共享模式 **loopback 于渲染端点**（不是采集端点） | `src/platform/windows/audio.cpp:391-393, 420, 493` |
| 请求格式 | **f32 / 48000Hz / 按目标声道数**（SAMPLE_RATE=48000，Opus 需要）；设备混合格式不同则由 Windows 转换 | `audio.cpp:54, 123, 83-132` |
| 转换方式 | `AUTOCONVERTPCM \| SRC_DEFAULT_QUALITY`——**委托 Windows 内置 SRC**（非高质量） | `audio.cpp:391-393` |
| 设备选择 | 默认匹配 **"Steam Streaming Speakers"**（adapter friendly name）；`virtual_sink` 配置可指定任意设备名 | `audio.cpp:871-889, 1087-1091` |
| 驱动方式 | 事件驱动（EVENTCALLBACK + SetEventHandle + WaitForSingleObjectEx，超时=设备周期） | `audio.cpp:605-612, 735-745` |
| 读包 | GetNextPacketSize 循环 drain；SILENT 标志→填零；DATA_DISCONTINUITY **仅记日志** | `audio.cpp:757-801` |
| 线程 | MMCSS "Pro Audio" | `audio.cpp:693-699` |
| 异常 | 设备失效/默认设备变更 → 完整 reinit | `audio.cpp:779-786, 808, 716-722` |
| 溢出 | 缓冲满→警告+截断（丢音频） | `audio.cpp:788-791` |

**对 Sunshine 的改进点（我们的质量优先级要求）**：
1. **不用 Windows 内置 SRC**：按 `GetMixFormat()` 的原生速率请求 f32（通常 48k）→ WASAPI 零转换；重采样由我们用 **rubato（windowed-sinc）** 完成——比 `SRC_DEFAULT_QUALITY` 高一个档次；
2. DATA_DISCONTINUITY 计入诊断计数（真机排障数据）；
3. 捕获缓冲按"永不丢音频"设计（大环 + 背压由 AirPlay pacing 侧消化，配合 splice 静音纪律）。

## 2. Q5：虚拟声卡候选（官方规格）

| 候选 | 来源 | 规格 | 二次 SRC 行为 | 成本 |
|---|---|---|---|---|
| **Steam Streaming Speakers** | 用户已装（Steam 附带） | 官方无规格文档；可配 5.1；Windows 面板可设默认格式（16/24bit）`[社区]` | 未知——**探针定** | 零（已装） |
| **VB-CABLE** | vb-audio.com 官方手册 | 内部固定 SR 可调（44.1/48/88.2/96/176.4/192k），I/O 8-192k，16/24bit；**两端速率=内部 SR 时零转换直通** | 速率不匹配才转 | 免费（donationware），已签名 |
| **HIFI-CABLE** | vb-audio.com 官方 | **bit-perfect**，最高 24bit/384kHz；要求输入输出同速率 | 无（bit-perfect） | 免费 |
| **VAC (Muzychenko)** | vac.muzychenko.net 官方 | 最高 384k/32bit/32ch，<1ms 延迟 | 格式转换可控 | 付费（完整版） |

**结论**：三候选规格均覆盖我们的需求（48k/立体声/f32 或 24bit）。决策用**探针实测**驱动：Steam Streaming Speakers 若呈现正常的 48k 立体声混合格式 → 直接用（零安装）；异常则推荐 VB-CABLE（内部 SR 设 48000）。软件不做设备绑定：枚举 + 用户可选 + 安装引导。

## 3. Q6：全链路音质上限分析

```
应用音频 ──(Windows 混音引擎, 必要时 SRC 至设备速率, 不可避免且所有方案相同)──▶
虚拟声卡 (48k f32) ──(WASAPI loopback, f32, 零转换)──▶ 捕获环 ──▶
rubato 48k→44.1k (windowed-sinc, 高质量) ──▶ TPDF 抖动至 16bit ──▶
ALAC 未压缩帧 (无损) ──▶ HomePod
```

- 仅有的有损环节：① Windows 混音引擎 SRC（系统级，不可消除）；② 我们的 rubato（高质量可控）；③ 16bit 量化（TPDF 抖动后透明）。
- 若 HomePod 广告 48k ALAC（决策 C 修订）：全链路 48k 直通，**环节②消除**，理论最优。
- 声道：立体声为目标；若设备为 5.1 配置，采集 f32 多声道后自行下混（或 AUTOCONVERTPCM 让 Windows 下混——下混质量可接受，与 SRC 不同）。

## 4. 决策门 D2（采集方案）

1. **采集**：WASAPI 共享模式 loopback 于选定渲染端点；请求 `GetMixFormat()` 原生速率 f32；事件驱动；MMCSS Pro Audio；大环形缓冲；discontinuity/溢出计数入诊断。
2. **转换**：rubato（SincFixedIn，高质量预设）→ 44.1k（或 hi-res 协商后 48k 直通）；TPDF 抖动量化 16bit；352 帧分包。
3. **设备策略**：枚举渲染端点 + 用户选择 + 持久化；默认自动探测 Steam Streaming Speakers→VB-CABLE→其他已知虚拟声卡；无虚拟声卡时给出安装引导。
4. **探针先行**（首个可交付程序即包含）：
   - `probe devices`：枚举全部渲染端点 + 混合格式 + 设备 ID（回答 Steam Streaming Speakers 真实格式）；
   - `probe airplay <ip>`：明文 **GET /info**（无需配对），取回 HomePod 能力表（格式表、features、protocolVersion）——hi-res 决策与 SETUP 参数的最终证据。
   - 依据：明文 GET /info 无需配对即可得，已经真机探针实证 `[实验: 06-真机探测-HomePod.md]`。
