# 研究笔记 02：AirPlay 协议调研（发送端方向）

> 证据标记：`[代码: 路径:行号]`（均为 `reference/repos/` 下固定 SHA 的本地副本）、`[文档: 出处]`、`[实验]`、`[假设]`。
> 仓库 SHA 见 `references/REFERENCES.md`。

## 1. 结论先行（D1 决策门 · 初步建议）

**建议选择 AirPlay 2（realtime 音频流，ALAC），回退方案为 AirPlay 1 (RAOP)。**

依据：
1. AirPlay 2 发送端的信息充分性已被代码级证据满足：存在**三个互相独立**的可运行 AP2 发送端实现（owntone-server [C]、airplay2-sender-cpp [C++]、airplay2-rs 系 [Rust]），关键步骤可互相印证（§3）。
2. 其中两个明确声称在真实 HomePod 上工作：AirSend（HomePod gen 2 + Windows 11 实测 [文档: README/Reddit]）、airplay2-sender-cpp（FXChainPlayer 产品日用 [文档: README]）。
3. AirPlay 2 realtime 的接收端行为有 shairport-sync 源码佐证（`type 96 → 硬编码 ALAC` `[代码: shairport-sync/rtsp.c:2862]`）。
4. 需求文档 §3.2：信息足够则优先更高版本 → AP2 满足该条件。

风险与未决项见 §5，其中"NTP vs PTP"与"保活机制"直接影响优先级第 1 位（稳定性），需在实现前关闭。

## 2. 协议格局

- 开源世界**接收端**充足（shairport-sync 8806★、airplay2-receiver 2343★），**发送端**稀缺且多为新项目。
- RAOP（AirPlay 1）发送端成熟（libraop、pyatv、owntone raop.c），但 HomePod gen 2 是否仍接受经典 RAOP 流**未证实**（§5.3）。
- AP2 发送端到 HomePod 的关键知识在 2025-2026 年才出现可验证的开源实现（airplay2-sender-cpp、airplay2-rs 系、AirSend）。

## 3. AP2 realtime 发送链路（代码级事实）

以 airplay2-sender-cpp（日用验证、文档最详）为主线，逐项标注其他实现的印证情况。

### 3.1 配对（两条路径）

| 路径 | 触发 | 流程 | 共享秘密 |
|---|---|---|---|
| HAP transient | HomePod / macOS（`sf=0x4`） | `/pair-setup` M1(Flags=0x10 transient)→M2(salt+B)→M3(SRP A,M1)→M4 止；固定 PIN **3939** | SRP 会话密钥 K=SHA-512(S)，**64 字节** |
| HAP PIN + pair-verify | Apple TV（`sf=0x644`） | `/pair-pin-start`→M1..M6（Ed25519 长期密钥交换）→`/pair-verify` M1..M3（X25519） | X25519 ECDH，**32 字节** |

- 代码：`airplay2-sender-cpp/src/raop_sender.cpp:1315-1595`（M1-M6、verify M1-M3、HKDF "Pair-Setup-Encrypt-Salt"/"Pair-Verify-Encrypt-Salt"、TLV8、nonce "PS-Msg05/06"、"PV-Msg02/03"）。
- HomePod 走 transient 路径（固定 PIN 3939）：`raop_sender.cpp:1082-1087, 1366-1369`；AirSend 同 `[代码: AirSend/crates/airplay-core/src/pairing.rs:13]`。
- **音频密钥 shk = 共享秘密的前 32 字节，直接使用（无 HKDF）**；transient 的 64 字节 K 须截断为 32，否则逐包抛错→无声→~30s 掉线：`raop_sender.cpp:1684-1711`；owntone 印证 `[代码: owntone-server/src/outputs/airplay.c:98,1444-1460]`，shk 明文放入 stream SETUP plist `[代码: airplay.c:2630]`。
- 470 → transient 被拒则回退 PIN 路径；403 → PIN 被拒可试 transient：`raop_sender.cpp:1138-1175`。

### 3.2 加密控制通道

- pair-verify/transient 完成后，**后续所有 RTSP 立即转 ChaCha20-Poly1305 加密帧**：`[2B LE 长度][密文][16B tag]`，AAD=长度前缀，nonce=`[4B 0][8B LE 计数器]`，收发独立计数器；密钥 HKDF-SHA512("Control-Salt","Control-Write|Read-Encryption-Key", K, 32)。不做则对方在 pair-verify 后立刻断连 `[代码: raop_sender.cpp:1252-1277（启用）, 695-740（解密帧）, 1379-1401（transient 下推导）]`。

### 3.3 会话建立顺序（"owntone 顺序"）

`GET /info → SETUP(session) → 开事件通道(eventPort) → RECORD → SETUP(stream) → 开始发流` `[代码: raop_sender.cpp:1620-1760]`

- 必须是 RTSP **方法**（`SETUP rtsp://…`），不是 `POST /setup`（404）`[代码: raop_sender.cpp:1589-1595]`。
- SETUP 头带 `X-Apple-StreamID: 1`；session SETUP plist 含 deviceID/sessionUUID/timingPort/timingProtocol/model(iPhone14,3)/osVersion(16.5)/sourceVersion(690.7.1) 等（发送端伪装 iPhone）`[代码: raop_sender.cpp:1626-1655]`。
- 事件通道是**反向 TCP 连接**（sender 主动连 receiver 的 eventPort）`[代码: raop_sender.cpp:1656-1675]`。
- RECORD 在 session SETUP 之后、stream SETUP 之前；RECORD 被拒（500）仍继续 stream SETUP `[代码: raop_sender.cpp:1120-1128, 1676-1683]`。
- owntone 侧印证：`airplay.c:142-171`（状态机含 RECORD 态）、`airplay.c:2654,3031-3033`（payload_make_record / 响应处理）。

### 3.4 音频流（realtime, type 0x60）

- **接收端硬编码 ALAC**（ct/audioFormat 被忽略）`[代码: shairport-sync/rtsp.c:2862]`。
- 两种可行负载（均无损）：
  - **未压缩 ALAC 帧**（airplay2-sender-cpp）：比特布局 `3b CPE=1 · 4b 0 · 12b 0 · 1b hasSize=0 · 2b 0 · 1b isNotCompressed=1 · 352×{L16,R16} MSB-first · 3b END=7 · 字节对齐` `[代码: raop_sender.cpp:1814-1837]`。
  - **压缩 ALAC**（airplay2-rs 用 `alac_encoder` crate + magic cookie）`[代码: airplay2-rs-pabldi08/crates/airplay-audio/src/encoder.rs:38-77]`；cookie 须放入 SETUP `asc`（AirSend 做法 `[代码: AirSend/.../streaming.rs:100-106]`）。
- stream SETUP plist：`audioFormat=0x40000, ct=2, spf=352, sr=44100, type=0x60, shk=<32B>, latencyMin/Max, streamConnectionID=RTSP 会话号` `[代码: raop_sender.cpp:1713-1739]`。
- RTP：12B 头（0x80/0x60，首包 marker 0xE0），SSRC=sessionId；**负载加密**：ChaCha20-Poly1305，AAD=头[4..12]，nonce=8B LE 计数器并**追加在密文+tag 之后** `[代码: raop_sender.cpp:1772-1789, 1838-1883]`。
- 节奏：按墙钟令牌桶 44100 帧/s `[代码: raop_sender.cpp:1791-1812]`；断料时填静音保持时间线 `[代码: raop_sender.cpp:1885-1912]`。

### 3.5 保活（两个独立机制，证据冲突，见 §5.2）

- **事件通道服务**（airplay2-sender-cpp）：解密 receiver 推送的 `POST /command`（帧格式同控制通道；密钥 HKDF "Events-Salt"/"Events-Write|Read"，**读写对调**），回复**最简 200 OK**（仅 Server + 可选 CSeq；多余头会导致"连着但无声"）；不做则 ~25-30s 被拆 `[代码: raop_sender.cpp:615-693, 1576-1582]`。
- **周期 feedback**（airplay2-rs/AirSend）：每 2s RTSP `POST /feedback`，声称 ~10s 无流量即断 `[代码: AirSend/.../streaming.rs:37-40, 276-318]`。

### 3.6 重传与同步

- 重传：sender 保留 backlog 环；receiver 在 controlPort 发 type 0x55 请求，回 0xD6+原始整包 `[代码: raop_sender.cpp:1876-1883, 1976-2006]`。
- 同步：type 0xD4 sync 包把 RTP 时间映射到 NTP 墙钟（含 latency 偏移）`[代码: raop_sender.cpp:1956-1975]`。
- 计时（NTP 模式）：sender 跑 timing UDP server，应答 receiver 的 32B timing 请求（0xD3 回显 reftime + recv/send 时间戳）`[代码: raop_sender.cpp:2007-2033]`；airplay2-rs 同 `[代码: connection.rs:731-740]`。
- 计时（PTP 模式）：airplay2-rs 实现 PtpMaster + BMCA `[代码: connection.rs:741-749]`；owntone 内置 ptpd，`SupportsPTP`(bit41) 存在时选 PTP `[代码: airplay.c:4066, 2752]`。

## 5. 未决问题（按对优先级的影响排序）

### 5.1 NTP vs PTP（HomePod gen 2）⚠️ 最关键
- 证据冲突：AirSend 用 NTP 声称 gen2 可用 `[代码: streaming.rs:117]`；jburnhams 文档称 HomePod **gen 1** SETUP 必须 PTP（NTP 超时）`[文档: airplay2-rs-jburnhams/findings.md]`（该文档疑似 AI 生成，可信度低）；owntone 在 `SupportsPTP` 时选 PTP `[代码: airplay.c:4066]`；airplay2-sender-cpp 用 NTP 且 README 声称支持 HomePod。
- AirSend 硬编码的 HomePod TXT features `0x4A7FCA00,0x3C354BD0` 中 bit41(SupportsPTP)=1 → gen2 支持 PTP；NTP 是否被 gen2 接受、长期稳定性如何，只能真机验证。
- 处置：实现时**两者都准备**（airplay2-rs 已有双实现可参考），默认策略待真机测试（用户测试节点）定夺。

### 5.2 保活机制：事件通道 vs feedback
- 见 §3.5。两个实现各执一词；AirSend 不做事件通道服务（仅连接）`[代码: connection.rs:797-807]`，Reddit 用户报告"播一会儿崩溃" `[文档: reddit_airsend.html]`——与 airplay2-sender-cpp 的"~30s 拆线"经验吻合。
- 处置：**实现事件通道完整服务**（证据更硬：日用产品 + owntone 印证），feedback 作为补充。此为稳定性优先级的直接体现。

### 5.3 HomePod gen 2 是否接受经典 RAOP（AP1 回退可行性）
- 未证实。jburnhams 文档称 HomePod 同时广播 `_raop._tcp` `[文档: airplay2-homepod.md]`；babelpod 用经典 airtunes2 RAOP 声称支持 HomePod（2023，未经活跃验证）`[代码: babelpod/package.json]`。
- 处置：若 AP2 路线受阻，再投入验证；不作为首选。

### 5.4 AP2 buffered 流（大缓冲、高音质潜力）
- emanuelecozzi 文档区分 realtime/buffered `[文档: airplay2-internals/index_audio.html]`；owntone AP2 亦实现 buffered（type 103? `rtsp.c:2062` 提及）。buffered 可能对稳定性/音质更有利（TCP 可靠传输），延迟更高。
- 处置：第二阶段评估——若 realtime 稳定性不达标，buffered 是候选。延迟优先级最低，可接受。

## 7. 决策记录（用户确认）

- **2026-08-12 决策 A（技术栈与代码基础）**：Rust；规范驱动自研（选项 α）——协议行为以研究笔记 §3 为规范，airplay2-sender-cpp 为消息格式第一参照，owntone/shairport-sync 为边界行为仲裁；**禁止依赖 airplay2-rs 全系及 AirSend**（AI 代码不可信、事件通道缺陷已证伪）；依赖白名单制（RustCrypto 家族、mdns-sd、windows crate、rubato、tokio；SRP-6a/TLV8/bplist/ALAC-未压缩帧自实现）；NTP 先行，PTP 推迟至真机证据要求时。
- **2026-08-12 决策 B（流类型）**：realtime (type 0x60) 定为唯一路线，buffered (type 103) 不投入研究。依据：①全部可用发送端均 realtime；②buffered 无发送端参考实现、文档为空；③协议本质分析（TCP 大缓冲/文件点播语义 vs UDP 小缓冲/直播语义）表明即使可得性相同，realtime 也更匹配"直播源+延迟有界"需求；buffered 的抗抖动优势可由调大 realtime 协商窗口（500ms-3s 档）获得大半。真机实测 realtime 稳定性不达标时复议。
- **2026-08-12 决策 C（音质天花板）**：44.1kHz/16bit/立体声 ALAC，落定。调研结论：Apple 自家发送端抓包中 stream SETUP 无 `sr` 字段（隐含 44100）`[文档: airplay2-internals/index_rtsp.html]`；无任何实现/资料支持发送端 48k 或 24bit；Apple 官方 24/48 无损仅限 HomePod 本体播放 Apple Music，与 AirPlay 发送无关 `[文档: support.apple.com 118295]`。音质预算改投：高质量重采样（rubato）、位深转换抖动、虚拟声卡二次 SRC 排查（阶段二）。
- **2026-08-12 决策 D（虚拟音频设备策略）**：采纳 D1——不自研驱动，依赖第三方虚拟声卡；软件枚举渲染端点+引导用户选择，WASAPI loopback 采集。理由：Windows 11 驱动签名门槛（EV 证书+attestation）与 KISS/稳定性目标冲突。用户环境已安装 Steam Streaming Speakers，但**不预设选用**；阶段二须对候选虚拟声卡做音质调研（原生格式/位深、驱动二次 SRC、环路延迟）后定推荐。
- **2026-08-12 决策 E（配对与认证范围）**：用户 HomePod 访问控制为"所有人/同一网络中的任何人" → transient 配对（PIN 3939）可行。**仅支持无密码/无认证路线**：不实现 digest auth、不实现 HAP 持久配对（PIN 路径）；receiver 返回 401/403/470 时给出明确可操作的错误提示（指引用户修改 AirPlay 访问设置），不静默失败。
- **2026-08-12 决策 C 修订（用户批准）**：默认 44.1kHz/16bit/立体声保底；架构预留格式协商（明文 GET /info 探测设备能力），hi-res（48/16/2=0x100000、44.1/24/2=0x80000、48/24/2=0x200000）仅在设备广告支持时启用，真机验证。依据：airplay-cli 代码实现并声称验证 hi-res realtime `[代码: airplay-cli/src/ap2_client.c:1320-1329]`；MA README 称 24bit 自动启用于广告设备；反例教训"SETUP 200≠有声"→ 按设备广告启用 `[文档: airplay-cli/DESIGN.md §11]`。
- **2026-08-12 决策 E 修订（用户批准）**：首版仅 transient（PIN 3939）无密码路线；**HAP PIN pair-setup + pair-verify + 凭证持久化降级为已批准应急预案，触发条件=真机 transient 失败**。依据：后向兼容论证（transient 是十年存量设备连陌生 HomePod 的唯一机制，苹果不可能移除）；airplay-cli "transient 无声"实测可用单方实现 bug 解释（M4 后多发 M5→TLV error；密钥错→加密无声）`[假设]`。配套：首版诊断做足（配对每步结果/TLV 错误内容/SETUP 响应全文/RTP 发送计数入日志），确保一次真机测试即可远程判定失败点。
- **2026-08-12 实施默认项（用户批准）**：
  1. **里程碑切分**：① 探针 CLI（枚举声卡 + HomePod /info）→ ② 可播放 CLI（配对+推流，用户测试节点）→ ③ 托盘 GUI；
  2. **hi-res 启用顺序**：即使探针显示 HomePod 广告 hi-res，首版仍先 44.1/16/2 建立基线，稳定后经配置开 hi-res 试；
  3. **延迟窗口默认**：latencyMin=11025 / latencyMax=88200（250ms~2s，Apple/owntone 惯例）；降档风险自负（<500ms Wi-Fi 下实测"机器人化"）；
  4. **发现双通道**：mDNS 发现 + 手动 IP 输入保底；
  5. **v1 不做**：元数据/now-playing、多声道、MediaRemote、设备密码、PTP（触发条件=真机证明 NTP 不可行）、PIN pair-setup（触发条件=真机证明 transient 不可行）；
  6. **断流恢复**：keepalive miss×3 或 RTP 错误 → 新连接重配（每次配对新 socket）→ 自动恢复推流，指数退避；全程静音续传（splice 纪律）；
  7. **交付形态**：单 exe 便携版 + 日志文件（机器可读状态行 + 详细 tracing）；用户反馈=日志。
