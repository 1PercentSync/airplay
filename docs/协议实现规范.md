## 链路总览与顺序

```
mDNS/手动IP → 明文 GET /info → [新 TCP] transient 配对 M1-M4 → 同连接加密通道
→ SETUP(会话) → 事件通道(反向 TCP) → 〔顺序分歧点 §6.3〕 → SETUP(流) → SET_PARAMETER(音量)
→ UDP: 音频(0x60) / sync(0xD4 1s) / timing server(0xD2→0xD3) / 控制(0xD5→0xD6) / POST /feedback 2s
→ TEARDOWN
```

## 4. HAP 加密通道帧

帧 = `[2B LE 明文长][密文][16B tag]`；每块明文 ≤1024；nonce = 4 字节零 + 8 字节小端计数器；收、发计数器独立；AEAD 附加数据 = 那 2 字节长度。配对成功后**同一条 TCP** 上，先把整份 RTSP 明文封成帧再写；读则先拆帧解密，再在明文缓冲里解析 RTSP（禁止再对 TCP 逐字节扫 `\r\n\r\n`）。

| 参考 | 结论 |
|---|---|
| owntone | 有：`ENCRYPTED_LEN_MAX 0x400`；`encrypt` 按块写 `uint16 block_len`（主机序，Windows/Linux 小端即 LE）+ ChaCha20-Poly1305，AAD=`&block_len` 共 2 字节，tag 16 字节跟在密文后；nonce 12 字节先清零再 `memcpy(nonce+4, &encryption_counter, 8)`（小端主机即 4 零+LE 计数）；每块计数 +1。`decrypt` 对称。`rtsp_cipher` 把整份 RTSP 明文交给 `pair_encrypt` 再写入套接字 `[代码: owntone pair_homekit.c:53-56,2944-3051; airplay.c:1005-1045]` |
| pyatv | 有：`HAPSession.FRAME_LENGTH=1024`、`AUTH_TAG_LENGTH=16`；`encrypt`：`length = len(frame).to_bytes(2,'little')`，AEAD 的 aad=length，输出 `length + ciphertext+tag`。`decrypt` 从缓冲取 2 字节 LE 长度再取 `n+16`。`Chacha20Cipher` 默认 8 字节计数，左垫 4 零成 12 字节 nonce；收发计数独立。挂到 `HttpConnection.send_processor`/`receive_processor`，同一条连接 `[代码: pyatv hap_session.py:17-66; chacha20.py:15-73; http.py:385-387,457; airplay/auth/__init__.py:112-115]` |

### 6.2 事件通道建立

## 7. 计时

### 7.1 timing server：应答 0xD2 → 32B 0xD3

发送端在会话 SETUP **之前**打开本地 UDP timing 口，把该端口写入会话 SETUP 的 `timingPort`。配件向该口发 32 字节 0xD2，发送端回 32 字节 0xD3。

| 参考 | 结论 |
|---|---|
| owntone | 有。进程初始化就 `service_start(timing_svc)`。请求须恰好 32 字节且 `[0]=0x80 [1]=0xd2`。应答：`[0]=0x80 [1]=0xd3 [2]=req[2] [3]=0`；`[8..16]=req[24..32]`（origin 回显）；`[16..24]` 接收 NTP；`[24..32]` 发送 NTP `[代码: owntone airplay.c:2262-2338,4313-4314]` |
| pyatv | 有。`TimingPacket.encode(req.proto, 0x53\|0x80, 7, 0, req.sendtime, recv, recv)`。seq 字段**恒 7**，不回显请求的 seq。接收端显然不校验该字段 `[代码: pyatv protocols/raop/protocols/__init__.py:102-140]` |
| shairport-sync | 有但是角色相反（接收端主动发 0xD2）：`rtp_timing_sender` 把 `req.type = 0xd2` 发向发送端 timing 口 `[代码: shairport-sync rtp.c:595-613]`。佐证请求类型是 0xD2 |
| raop_sender(C) | 有。请求须 ≥32 字节；应答回显 `dg[0]`、类型 0xD3、seq `0x0007`、reftime=`dg.mid(24,8)`、recv/send 均为当前 NTP `[代码: raop_sender.cpp:2007-2031]`。seq 恒 7，近 pyatv |
| airplay2-receiver | 无独立 NTP 应答实现。`EventGeneric.spawn(..., name='ntp')` 与事件通道共用同一套只 accept 的 TCP 占位，不是 UDP 0xD2 `[代码: airplay2-receiver ap2-receiver.py:536-538]` |
| libraop | 有但是路线不同：AP1 请求类型 `0x52\|0x80`（不是 0xD2）；timing 线程在 ANNOUNCE/SETUP **之前**启动 `[代码: libraop raop_streamer.c:763-772; raop_client.c:1025-1036]`。不搬类型；“SETUP 前先开 timing 口”可作背景 |

### 7.2 sync 包（20B，1s 节奏，首包 0x90 后续 0x80）

布局：`[0]=type [1]=0xD4 [2..4]=0x0007 [4..8]=当前播放位置 BE [8..16]=NTP 秒+小数 BE [16..20]=当前 rtptime BE`。发到流 SETUP 返回的 `controlPort`。

| 参考 | 结论 |
|---|---|
| owntone | 有。`sync_packet_ntp_make`：`data[1]=0xd4`，`data[2..4]=0x0007`；位置字段 = `cur_stamp.pos`；尾 4 字节 = 起始 `pos`（须与 RTSP 告知的起始 rtptime 一致）。刚加入的设备发 `0x90`，之后 `0x80` `[代码: owntone rtp_common.c:309-344; airplay.c:2185-2194]` |
| pyatv | 有。`SyncPacket.encode(0x90 或 0x80, 0xD4, 0x0007, rtptime−latency, ntp, rtptime)`；循环 `sleep(1.0)` `[代码: pyatv stream_client.py:107-134]` |
| shairport-sync | 有（接收端消费）：`packet[1] == 0xd4` 当 sync `[代码: shairport-sync rtp.c:344]`。佐证类型 0xD4 |
| raop_sender(C) | 有。20 字节：首包 `0x90` 其后 `0x80`，类型 `0xD4`，`be16(0x0007)`，位置 `now-latency`，NTP，`now`；发到 `controlPort` `[代码: raop_sender.cpp:1956-1973]` |
| airplay2-receiver | 无发送端 sync。控制口在 `Control` 进程，不构造 0xD4 |

| rust-raop-player | 有但是路线不同：`type_: 0x54 \| 0x80` `[代码: rust-raop-player rtp.rs:59]`。不搬 |
| babelpod | 无 |
| airplay-spec | 背景：payload 84 = time sync `[文档: rtp_streams.md]`。84=0x54。不作 AP2 结论 |
| Sunshine / AudioMirror | 无 |
| 真机 | 2026-08-13 `run` 出声；未单独打印 0xD4 发送 |

**选定**：20 字节、1 秒一发、首包 0x90 其后 0x80、类型 0xD4、位置 = rtptime−latency（pyatv 与 raop_sender 一致）。owntone 的位置字段语义略不同，以 pyatv 为准（双源：pyatv + C 级同构；owntone 注释写 AP2 不使用 0x0007 那两字节，改由 latencyMin 协商）。

### 7.3 时间模型（44.1kHz 下）

- NTP 定点：`ntp2ts(n) = ((n >> 16) * rate) >> 16` `[代码: pyatv raop/timing.py:24-31]`
- latency（lead）= 22050 + 44100 = **66150**（1.5s）`[代码: pyatv raop/protocols/__init__.py:28,51]`
- 锚点：start_ts = ntp2ts(now)；rtptime = head_ts − (start_ts − latency) = 66150 + 已发帧数 `[代码: pyatv raop/protocols/__init__.py:48-57]`
- 协商窗口：66150 档 latencyMin=11025 / latencyMax=88200（owntone airplay.c:2628-2629 与 pyatv airplayv2.py:136-137 一致）。短档（5292/7938/10584/13230/15876）按用户方案 min=0、max=lead×2。真机：这台 HomePod AP2 RECORD 不回 `Audio-Latency`；min 可写 0；lead 4500 不能播、5000 能播；体感延迟跟 lead，不跟当时仍为 88200 的 max。
- owntone 注释给出启动时 rtptime 关系：sync 的 rtptime、音频首包、RECORD 告知值应对齐 `[代码: owntone airplay.c:2119-2127]`
- raop_sender 用同一套 `ts2ntp` / `latency_`（C 级同源 pyatv）
- libraop / rust-raop-player / babelpod / airplay-spec / Sunshine / AudioMirror / airplay2-receiver：无这套 AP2 锚点公式
- 真机：2026-08-13 `run` 出声。后续用户测：RECORD 无 `Audio-Latency`；min=0 可播；lead 4500 不能播、5000 能播；体感跟 lead

**选定**：默认档仍用 pyatv 锚点（lead=66150）+ 双 A 级窗口。托盘六个预设见 `LATENCY_PRESETS`；短档窗口按用户方案。

### 8.2 ALAC 未压缩帧（16bit 立体声）

| raop_sender(C) | 有。手写位写器：3+4+12+hassize+wasted+isNotCompressed+样本+END=7 `[代码: raop_sender.cpp:1814-1835]`。与 shairport 解码器逐比特一致 |

### 8.3 加密与线上布局

`[12B RTP 头][ct+16B tag][8B nonce 尾附]`；AAD = 头[4..12]（rtptime+SSRC）；ChaCha20-Poly1305 IETF；key=`shk`。

| 参考 | 结论 |
|---|---|
| owntone | 有。nonce 12 字节先清零，再 `memcpy(nonce+4, &pkt->seqnum, 2)`——**用 RTP 序号当 nonce**（注释：重发包须与原包逐字节相同）。AAD=`pkt->header+4` 长度 8。线上：原 RTP 头 + 密文 + tag + nonce 的后 8 字节 `[代码: owntone airplay.c:1916-1948]` |
| pyatv | 有。`Chacha20Cipher8byteNonce` 内部 8 字节计数器；`encrypt` 不传入 nonce 以便计数器自增；包尾附 `nonce[-8:]`。AAD=`rtp_header[4:12]`。注释写曾经发全零 nonce、Apple 不在意 `[代码: pyatv airplayv2.py:183-204; chacha20.py:50-88]` |
| shairport-sync | 有（接收端）：`decipher_player_put_packet` 把传入缓冲当成从 seq 起的 RTP（即跳过版本/PT 两字节后）：密文从 +10 开始（相对完整包即 +12），AAD 为 +2 起 8 字节（时戳+SSRC），尾 8 字节填入 nonce[4..12] `[代码: shairport-sync rtp.c:1555-1594]`。nonce 以包尾为准，不强制等于 seq |
| raop_sender(C) | 有。nonce = 内部 `audioNonce` 计数器（pyatv 风格，不是 seq）；AAD=头[4..12]；尾附 8 字节 nonce `[代码: raop_sender.cpp:1772-1786]` |
| airplay2-receiver | 有（接收端）：`ChaCha20_Poly1305.new(..., nonce=rtp.nonce)`，`update(rtp.aad)` `[代码: airplay2-receiver audio.py:544-548]` |
| libraop / rust-raop-player | 无 ChaCha RTP。AP1 AES-CBC |
| babelpod / airplay-spec / Sunshine / AudioMirror | 无此布局 |
| 真机 | 2026-08-13 `run` 出声（ChaCha RTP 布局被接受） |

**选定**：nonce 的 8 字节尾附按 owntone：把 `uint16` seq 按主机小端写在前两字节，其余六字节为 0（`memcpy(nonce+4, &seqnum, 2)` 后截 nonce[4..12]）。这样重发包与原包逐字节相同。AAD = 头[4..12]。shairport 按包尾 8 字节解密，不要求 nonce 等于 seq。

**音量锁定**（决策记录·默认项 8：播放期间保持软件设定值）。先对照各发送端有没有用 `GET_PARAMETER` 去锁：

`GET_PARAMETER` 是 RTSP 方法，body 为 `volume\r\n` 时接收端回当前 dBFS。发生在已经建立的加密控制通道上，用来读接收端音量，不是用来推流。

| 参考 | 播放中如何维持音量 |
|---|---|
| owntone | 用户改音量时 `SET_PARAMETER`。不轮询 `GET_PARAMETER`。evrtsp 注释写明部分设备不支持或会挂起（例 `RAOP_DEV_APEX1_80211G`）`[代码: owntone evrtsp/evrtsp.h:63]` |
| pyatv | 推流前若给定音量则 `SET_PARAMETER` 一次 `[代码: pyatv stream_client.py:370-373,450-451]`。仓库内无 `GET_PARAMETER` |
| raop_sender(C) | 流开始时 SET 一次 `[代码: raop_sender.cpp:978-995]`。无 GET |
| libraop / rust-raop-player | AP1 SET；libraop 服务端 OPTIONS 广告 GET，发送端 `raopcl_repair` 重连时可再 SET `[代码: libraop raop_client.c:1159-1177]`。不轮询 GET |
| shairport-sync | 接收端：`GET_PARAMETER` body 恰好 `volume\r\n` 时回 `volume: %.6f` `[代码: shairport-sync rtsp.c:3305-3325]` |

| airplay-spec / Sunshine / AudioMirror | 无 AirPlay 音量锁 |

**选定（锁）**：不用 `GET_PARAMETER`（owntone 挂起警告；在册发送端都不靠它锁）。每约 2 秒再发一次 `SET_PARAMETER`（与 `/feedback` 同一任务）；GUI 改音量时立刻再发。用户已授权定时重设。HomePod 是否接受重复 SET `[未验证]`（GUI 测试点）。

**Windows 混音器 → HomePod**：Sndvol 设备滑条走 `IAudioEndpointVolume` `[文档: research/references/ms_volume_controls.md]`。Sunshine 采集链没有再乘端点音量 `[代码: Sunshine audio.cpp]`。

抽头位置：

| 条件 | loopback 里有没有设备滑条 |
|---|---|
| 无硬件 loopback pin（虚拟声卡常见） | WASAPI 把引擎送去 render pin 的那份再拷一份给我们 `[文档: research/references/ms_loopback_recording.md]` |
| 设备没有硬件音量 | 系统用软件音量替代 `[文档: research/references/ms_query_hardware_support.md]` → 这份引擎输出已经含滑条 |
| 设备有硬件音量 | 衰减在 DAC，引擎输出仍是满幅 → loopback 通常不含滑条 |

2026-08-13 托盘真机：Steam Streaming Speakers 上我们又乘了一次标量（日志 `endpoint gain` 从 0.30 到 1.0）。系统音量「有用」在乘一次和乘两次时都会成立；按上表，这块虚拟声卡是软件音量，**算了两次**。

**选定（端点增益）**：`QueryHardwareSupport`，仅当 `ENDPOINT_HARDWARE_SUPPORT_VOLUME`（0x1）置位才把标量乘到 PCM。未置位则增益固定 1.0，让 loopback 自带的软件音量生效一次。Steam Streaming Speakers 预期走不乘。改完后的真机曲线 `[未验证]`。

**音量回读与监听**（事实基础）：
- 事件通道无音量推送（§6.2）→ 不能被动监听接收端音量变化。
- 读取惯例存在（上表 shairport `GET_PARAMETER`），HomePod 是否支持 `[未验证]`。本实现不走这条。

## 16. 探针原语（TLV8 / SRP 公式 / bplist / RTSP 帧）

> 本节是 2026-08-13 全参考重读后写入。三个测试节点仍是探针 CLI / 可播放 CLI / 托盘 GUI。探针命令 `devices`/`discover`/`airplay`/`pair` 用 §16.1–16.4 和 §1、§2、§5、§12.1。§16.5 是配对后控制通道加密（`probe channel` 是探针程序里的一条命令，不是第四个测试节点）。可播放 `run` 已于 2026-08-13 真机出声。

### 16.1 TLV8

规则：一字节 type、一字节 length（0–255）、value；同一 tag 连续分片，读时拼接。空 value 仍发 type+0。

| 参考 | 结论 |
|---|---|
| pyatv | `read_tlv` 把**所有**同 tag 拼进 dict（不要求相邻）；`write_tlv` 按 255 切 `[代码: pyatv hap_tlv8.py:77-123]`。Type：Method=0, Salt=2, PublicKey=3, Proof=4, SeqNo/State=6, Error=7, Flags=0x13；Flags.Transient=0x10 |
| owntone / shairport-sync | `pair-tlv.c`：写按 255 切；读只把「连续 255 块 + 同 type 收尾块」拼在一起 `[代码: owntone pair-tlv.c:116-207]`。Type 与 pyatv 同（Flags=19）；FragmentData 写成 13（HAP 规范是 12）——M1–M4 不用 Fragment |
| raop_sender(C) | 同 HAP 分片；decode 只拼接**紧邻**同 tag `[代码: airplay_crypto.cpp:404-438]` |
| airplay2-receiver | `Tlv8.decode` 同 pyatv（所有同 tag 拼接）；`encode` 接受 `[tag, value, tag, value, ...]` 列表 `[代码: hap.py:74-128]` |
| 其余在册参考 | 无 HAP TLV8 |

**选定**：编解码按 pyatv/airplay2-receiver（同 tag 全拼接，更容忍）。写出：len==0 发一条零长记录；len>0 按 255 切、不额外发零长尾（避免 airplay2-receiver `length % 255 == 0` 再写一条 0 的行为）。探针只用 Method/State/Salt/PublicKey/Proof/Flags/Error。

### 16.2 SRP-6a 客户端公式（HAP transient）

共同约定（双 A 级 + RFC 5054 A.4 + 真机）：N=3072-bit RFC 5054、g=5、SHA-512、I=`Pair-Setup`、P=`3939`、salt 16 字节、公钥 ≤384 字节、证明 64 字节。

| 量 | owntone `pair_homekit.c` / `pair.c` | raop_sender `airplay_crypto.cpp` | airplay2-receiver `srp.py`（服务端） |
|---|---|---|---|
| k | `H_nn_pad(N,g,N_len)`：两操作数左填到 384 再 SHA-512 `[pair.c:192-216]` | 同 PAD `[282-325]` | `H(N,g,pad=True)` |
| u | `H_nn_pad(A,B,N_len)` | 同 | `H(A,B,pad=True)` |
| x | `H_ns(salt, H(I:P))`：salt 当大数再 **去掉前导零** 后哈希 `[pair.c:218-232; pair_homekit.c:269-281]` | **原始 salt 字节**（不去前导零）`[327-336]` | salt 当 int，`to_bytes` 去前导零 |
| K | `hash_num(S)`：S 去前导零再 SHA-512，64 字节 `[508]` | 同「自然长度」`[352-353]` | `H(S)` 去前导零 |
| M1 | `H( H(N) xor H(g) \| H(I) \| s \| A \| B \| K )`，N/g/s/A/B 均去前导零 `[284-314]` | s/A/B 用自然长度；**s 用原始 salt 字节** `[355-373]` | 同 owntone（int 去零） |
| HAMK | `H(A \| M1 \| K)` `[316-327]` | 同 `[383-397]` | 同 `H(A,M1,K)` |
| A 上线 | `bnum_num_bytes(A)`，**不**填到 384 `[447-458]` | `mpi_write_binary` 自然长度 `[307-308]` | `to_bytes(B)` 自然长度 |
| S | `(B - k*g^x) ^ (a+ux) mod N`；减后**未**先 `mod N` `[500-506]` | 减后显式 `mod N` 保正 `[338-350]` | 服务端 `(A * v^u)^b mod N` |

**选定**：k/u 用 RFC 5054 PAD（三家一致）。x/M1 的 salt 与 A/B/S/N/g 按 owntone 去前导零（A 级；与 airplay2-receiver 一致；不跟 C 级「原始 salt 字节」）。S 底数减完后模 N（RFC 5054 数学形式；raop_sender 显式做了；owntone 依赖 BN_mod_exp 吃负数）。`a` 256 bit（owntone `bnum_random(a,256)`）。A 上线：自然长度，接收端检查 `size > 384` 才拒（owntone `pair_homekit.c:1436`），不强制填 384。安全检查：B≠0、u≠0。HAMK 用 `==` 比较（LAN + 公开 PIN；用户已定不改恒定时间）。

pyatv 的 `srptools` 是黑盒，行为以 owntone 为准。

### 16.3 bplist（探针只需解码 `/info`）

| 参考 | 结论 |
|---|---|
| pyatv | 编解码全部交给 CPython `plistlib.FMT_BINARY` `[代码: pyatv support/rtsp.py:10, 110, 287-288]`。整数：`tokenH==0x10`，宽 `1<<tokenL` 字节；`tokenL>=3` 按有符号；`tokenL==4` 读 16 字节。编码：`2^63..2^64-1` 写标记 `0x14` + 16 字节 `[文档: research/references/cpython_3.12_plistlib_int.md]` |

### 16.4 RTSP 请求帧（明文）

|---|---|

**选定**：`RTSP/1.0`；CSeq 从 0；DACP-ID 与 Client-Instance 为同一 16 位大写 hex（u64）；Active-Remote 为 u32 十进制；User-Agent `AirPlay/550.10`（用户原话保持 550）；另加 `X-Apple-Client-Name: airplay`（owntone/raop_sender 有，pyatv 无；接收端不校验）。有 body 才写 Content-Length 与 Content-Type。响应：读到 `\r\n\r\n` 后按 Content-Length 取二进制 body；状态码非 2xx 抛错。`GET /info` 无 body（owntone SEQ_START、pyatv `info()`、raop_sender `sendAp2Info_`）。shairport Stage 1 带 qualifier plist 是可选的另一形态，发送端三家都不发。明文路径允许对 TCP 扫头；加密开启后改走 §16.5。

### 16.5 控制通道 HAP 帧（配对后同连接）

输入：64 字节 SRP K。输出：同一条 TCP 上的加密 RTSP。

构造：HKDF-SHA-512 出 32 字节 Write/Read 钥（§3.1）。发送时把整份 RTSP 明文按 1024 切开；每块 `n = u16 LE(块长)`，nonce = 4 零 + u64 LE 发送计数，AAD = `n` 的两字节，ChaCha20-Poly1305 IETF，线上 `n || 密文 || 16B tag`，然后发送计数 +1。接收时先读 2 字节 `n`，再读 `n+16`，用 Read 钥与接收计数解密（AAD 同样是那 2 字节），拼进明文缓冲，再按 Content-Length 解析 RTSP。计数从 0 起，收发分开。

证据与选定见 §3.1、§4。探针命令 `probe channel`：新 TCP → 明文 M1–M4 → 同连接打开加密 → 加密 `GET /info`。本切片不实现事件通道（§3.2）。
