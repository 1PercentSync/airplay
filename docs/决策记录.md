## 一、五项大决策（2026-08-12 对话中批准）

### 决策 A：用什么技术栈写

**决定**：用 Rust，自己写协议代码，不依赖现成的 AirPlay 库。

具体来说：

- 语言用 Rust。
- 协议的每一个字节怎么发，以调研笔记里钉死的配方为准，自己实现。
- 外部依赖实行白名单制：只允许用主流成熟库——RustCrypto 家族的密码学库、mDNS 发现库 mdns-sd、微软官方 Windows 绑定库 windows、重采样库 rubato、异步运行时 tokio。
- 以下小组件自己写，不引依赖：SRP 配对握手、TLV8 和 bplist 两种数据格式、ALAC 音频帧。
- 时钟同步先用 NTP 方案；PTP 方案推迟，除非真机证明 NTP 不行。

**禁止**：airplay2-rs 系列库和 AirSend（AI 生成代码，不可信）。用户原话："airplay2-rs肯定不可能用,AI代码也不可信"（消息 123）。

**批准经过**：用户原话"采纳建议,下一个问题"（消息 125）。

**遗留**：当时的提议里写了"以 airplay2-sender-cpp 为消息格式的第一参照"。后来该项目可信度被降级（只能参考代码字面），第一参照应改为 owntone 和 pyatv。这处措辞修订尚未经用户批准，见文末"待批准修订"。

### 决策 B：用哪种流传输方式

**决定**：只用 realtime（实时流），不研究 buffered（缓冲流）。

理由：所有可参考的发送端实现都用 realtime；buffered 没有任何可参考的发送端代码。如果将来真机实测 realtime 稳定性不达标，可以重新讨论。

**批准经过**：用户原话"采纳建议,下一个"（消息 138）。

### 决策 C：音质做到什么程度

**决定**：44.1kHz / 16bit / 立体声，ALAC 无损编码。

**批准经过**：用户定的规则是"做研究,然后如果没有资料就44.1kHz/16bit/立体声"（消息 142）——先调研，没有资料支持更高规格就按这个定。调研结论是没有任何资料支持发送端用 48kHz 或 24bit，于是按此落定。省下的精力投在重采样质量、位深转换抖动、虚拟声卡的重采样排查上。

### 决策 C 的补充：预留高规格协商

**决定**：默认仍用 44.1kHz/16bit/立体声；代码里预留格式协商的余地——如果设备自己广告支持更高规格，可以开启并真机验证。

**批准经过**：用户原话"1.没问题"（消息 220）。

**后续**：当时支持这个补充的第三方资料后来被证伪；而且真机探测已确认用户的 HomePod 只广告 44.1kHz/16bit/立体声（见 `research/06`）。所以这条补充保留，但在本设备上不会触发。

### 决策 D：虚拟声卡怎么办

**决定**：不自己写驱动，用现成的第三方虚拟声卡；软件负责枚举设备并引导用户选择。

用户原话："D1,已安装Steam Streaming Speakers,但不代表我们就用Steam Streaming Speakers,做调研"（消息 157）——用户机器上已装 Steam Streaming Speakers，但具体用哪款要经过调研再定（调研已完成，见 `research/04`）。

### 决策 E：配对认证做到什么范围

**决定**：只支持"无密码、无认证"这一条路线。

用户原话："只需要支持无密码无认证的路线"（消息 161）。用户的 HomePod 访问控制设为"所有人 / 同一网络中的任何人"，满足这条路线的条件。

## 二、实施默认项（七条）

用户问过"有什么新的要决策的问题吗"，Agent 列出七条实施层默认方案，用户回复"行"（消息 258）确认。

1. **分三个里程碑做**：① 探针命令行（枚举声卡 + 读 HomePod 能力）→ ② 可播放命令行（交给用户测试）→ ③ 托盘图形界面。
2. **高规格音频的顺序**：就算设备广告支持高规格，第一版也先用 44.1kHz/16bit/立体声站稳，稳定后再通过配置开高规格试。
3. **延迟窗口默认值**：11025 ~ 88200 采样（约 0.25~2 秒）；用户自行调低的话风险自负。
4. **找设备的两条路**：mDNS 自动发现 + 手动输 IP 兜底。
5. **第一版明确不做**：元数据/正在播放、多声道、MediaRemote、设备密码、PTP（真机证明 NTP 不行才做）、PIN 配对（真机证明 transient 不行才做）。
6. **断流恢复**：检测到断流后自动用全新连接重新配对并恢复推流，重试间隔指数退避；恢复期间一直发静音，不出爆音。
7. **交付形态**：单个 exe 便携版 + 日志文件；用户测试后把日志交给 Agent 分析。
