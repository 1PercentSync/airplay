## 1. 结论先行（D1 决策门 · 初步建议）

**建议选择 AirPlay 2（realtime 音频流，ALAC），回退方案为 AirPlay 1 (RAOP)。**

依据（清理后）：
1. AP2 发送端知识有两个 A 级独立来源：owntone-server（C，量产服役）与 pyatv（Python，真机覆盖最广）；airplay2-sender-cpp（C 级，仅代码字面可作参照）。
2. **真机实证**：本项目探针已在用户 HomePod gen 2 上完成 transient 配对、加密通道、session SETUP、RECORD `[实验: 06]`——AP2-to-HomePod 链路存在性不再依赖任何第三方声称。
3. AirPlay 2 realtime 的接收端行为有 shairport-sync 源码佐证（`type 96 → 硬编码 ALAC` `[代码: shairport-sync/rtsp.c:2862]`）。
4. 需求文档 §3.2：信息足够则优先更高版本 → AP2 满足该条件。

## 2. 协议格局

- 开源世界**接收端**充足（shairport-sync、airplay2-receiver），**可信发送端**集中于 owntone 与 pyatv。
- RAOP（AirPlay 1）发送端成熟（libraop、pyatv、owntone raop.c），但 HomePod gen 2 是否仍接受经典 RAOP 流**未证实**（§5.3）。

## 3. AP2 realtime 发送链路（清理后证据状态）

### 3.1 配对（transient）

- `/pair-setup` M1(Flags=0x10 transient)→M2(salt+B)→M3(SRP A,M1)→M4 止；固定 PIN **3939**；共享秘密 = SRP 会话密钥 K=SHA-512(S)，64 字节 `[实验: 06（真机成功，HAMK 校验通过）; 代码: pyatv hap_transient.py]`。
- HAP 变体 SRP-6a 约定（RFC 5054 3072-bit、g=5、SHA-512、k/u/x/M1/HAMK 公式）：`[实验: 06]`，旁证 `[代码: owntone pair_homekit.c; pyatv hap_srp.py]`。
- **密钥派生**：控制+事件通道密钥 HKDF-SHA512 的 IKM = **完整 64B K**；音频密钥 shk = K 的前 32B `[代码: owntone airplay.c:1443（注释明示）, 2630; pyatv hap_transient.py encryption_keys]`。

### 3.2 加密控制通道

- 配对完成后所有 RTSP 转 ChaCha20-Poly1305 加密帧：`[2B LE 长度][密文][16B tag]`，AAD=长度前缀，nonce=`[4B 0][8B LE 计数器]`，收发独立计数器；密钥 HKDF("Control-Salt","Control-Write|Read-Encryption-Key") `[实验: 06（加密 GET /info 真机成功；首轮 IKM 截断错误即被立刻断连，反证）; 代码: owntone pair_homekit.c:2892-2940 cipher_new]`。

### 3.3 会话建立顺序

`GET /info（明文探针）→ 配对 → 加密 GET /info → SETUP(session) → 开事件通道(eventPort) → RECORD → SETUP(stream) → 开始发流` `[实验: 06（至 RECORD 真机逐步通过）; 代码: owntone airplay.c 会话序列; pyatv ap2_session.py:75-82]`

- SETUP 为 RTSP 方法（`SETUP rtsp://…`）`[实验: 06（200 响应）]`。
- session SETUP plist：owntone NTP 版仅 4 字段（deviceID/sessionUUID/timingPort/timingProtocol）`[代码: owntone airplay.c:2691-2716]`；airplay2-sender-cpp 的全字段伪装（model/osVersion 等）为 C 级做法——**多余字段实测未致害（200），重写以 owntone 最小集为基线** `[实验: 06]`。
- `timingProtocol` 不可为 "None"（ATV4 不响应流 SETUP）`[代码: owntone airplay.c:2705 注释]`。
- 事件通道 = 反向 TCP（sender 连 receiver 的 eventPort）`[实验: 06（连接建立、后续 RECORD 200）; 代码: pyatv ap2_session.py:138-148]`。

### 3.4 音频流（realtime, type 0x60）

- **接收端硬编码 ALAC**（ct/audioFormat 被忽略）`[代码: shairport-sync/rtsp.c:2862]`。
- 负载选择**未压缩 ALAC 帧**（KISS，无编码器依赖）：比特布局 `3b CPE=1 · 4b 0 · 12b 0 · 1b hasSize=0 · 2b 0 · 1b isNotCompressed=1 · 352×{L16,R16} MSB-first · 3b END=7 · 字节对齐` `[代码: raop_sender.cpp:1814-1837（C 级）]`——重写前须以 shairport-sync 内 ALAC 解码器（Apple 官方 alac.c 血统）或 FFmpeg 验证帧头比特序 `[待验证]`。
- stream SETUP plist 字段集：`audioFormat=0x40000, audioMode, ct=2, spf=352, sr=44100, type=0x60, shk=<32B>, latencyMin/Max, controlPort, isMedia, supportsDynamicStreamID, streamConnectionID` `[代码: pyatv ap2_session.py（stream SETUP 构造）]`。
- RTP：12B 头（0x80/0x60）；负载加密 ChaCha20-Poly1305，AAD=头[4..12)，nonce=序列号置 12B nonce 的 offset 4，尾部追加同 8B；`[12B 头][密文][16B tag][8B nonce]` `[代码: owntone airplay.c:1916-1950 packet_encrypt]`。首包 marker 0xE0 `[未验证（C 级来源）]`。
- 节奏：按墙钟 pacing 44100 帧/s；断料填静音保时间线 `[自定纪律]`。

### 3.5 保活（两个独立机制，A 级一致）

- **事件通道服务**：解密 receiver 推送的加密请求并应答；密钥 HKDF("Events-Salt","Events-Write|Read")，读写相对控制通道对调 `[代码: owntone pair_homekit.c:2904-2913; pyatv ap2_session.py:138-148]`。应答具体形状 `[未验证]`（重写前以 pyatv channels.py / owntone airplay_events.c 定稿）。
- **周期 feedback**：每 ~2s `POST /feedback`，**空 body** `[代码: pyatv support/rtsp.py:246, ap2_session.py:29; owntone airplay.c:3701]`。设备广告 keepAliveSendStatsAsBody=true `[实验: 06]`——统计 body 仅作可选增强，非必需（"必须统计 body"系 airplay-cli 孤证，已降级）。

### 3.6 重传与同步

- 重传：receiver 向 sender controlPort 发 type 0x55 请求，回 0xD6+原始整包 `[代码: raop_sender.cpp（C 级）; 待以 owntone 重传处理器验证]`。重传包须与原包字节一致 `[代码: owntone airplay.c:1931 注释]`。
- 同步：type 0xD4 sync 包映射 RTP 时间↔NTP 墙钟；节奏 ~1s；首包 0x90 后续 0x80 `[代码: owntone airplay.c:2184-2195]`。20B 布局细节 `[待读: owntone rtp_session 代码]`。
- 计时（NTP 模式）：sender 跑 timing UDP server，应答 32B timing 请求：`[0x80, 0xD3, req[2], 0, req[24..32] 回显, recv 时间戳, send 时间戳]` `[代码: owntone airplay.c:2262-2330 timing_svc_cb]`。计时服务须在流 SETUP 前就绪（owntone 的计时服务常驻、先于一切会话）`[代码: owntone airplay.c:4314]`。
- 计时（PTP 模式）：推迟；届时以 owntone PTP 会话代码为准 `[代码: owntone airplay.c payload_make_setup_session_ptp]`。

## 5. 未决问题（清理后状态）

### 5.1 NTP vs PTP（HomePod gen 2）——基本结案
- **真机**：`timingProtocol: NTP` 的 session SETUP 获 200 + eventPort 下发 `[实验: 06]` → NTP 被 gen 2 接受。当前流 SETUP 无响应的卡点与计时协议选择无关（SETUP 层已应答），原因在查（见 06 迭代记录）。
- PTP 维持推迟（决策默认项 5）。

### 5.2 保活机制——结案
- 双机制（事件通道 + 周期 /feedback）获 pyatv/owntone A 级一致支持（§3.5），定为实现规范。

### 5.3 HomePod gen 2 是否接受经典 RAOP（AP1 回退可行性）
- 未证实。babelpod（2023）声称可发 HomePod `[B 级]`；AP2 路线受阻时再验证。

### 5.4 AP2 buffered 流
- 决策 B 已定（realtime 唯一），buffered 不投入研究。

## 7. 决策记录（用户确认）

> **2026-08-12 清理批注（非决策变更）**：下列决策文本为用户批准原文，保持不变。其中对被移除项目的引用按 `07-参考清理.md` 处理：决策 A 的"禁止依赖 airplay2-rs 全系及 AirSend"已被后续事件证实正确；"airplay2-sender-cpp 为消息格式第一参照"在清理后降为 C 级参照（仅代码字面），A 级仲裁为 owntone/pyatv——此点构成对决策 A 措辞的**修订建议**，待用户批准。决策 C 修订中的 hi-res 依据已被真机结案取代（`06`：realtime 仅 44.1/16/2）。决策 E 修订中的 airplay-cli 分析已被真机实验取代（transient 成功）。

- **2026-08-12 决策 A（技术栈与代码基础）**：Rust；规范驱动自研（选项 α）——协议行为以研究笔记 §3 为规范，airplay2-sender-cpp 为消息格式第一参照，owntone/shairport-sync 为边界行为仲裁；**禁止依赖 airplay2-rs 全系及 AirSend**（AI 代码不可信、事件通道缺陷已证伪）；依赖白名单制（RustCrypto 家族、mdns-sd、windows crate、rubato、tokio；SRP-6a/TLV8/bplist/ALAC-未压缩帧自实现）；NTP 先行，PTP 推迟至真机证据要求时。
- **2026-08-12 决策 B（流类型）**：realtime (type 0x60) 定为唯一路线，buffered (type 103) 不投入研究。依据：①全部可用发送端均 realtime；②buffered 无发送端参考实现、文档为空；③协议本质分析（TCP 大缓冲/文件点播语义 vs UDP 小缓冲/直播语义）表明即使可得性相同，realtime 也更匹配"直播源+延迟有界"需求；buffered 的抗抖动优势可由调大 realtime 协商窗口（500ms-3s 档）获得大半。真机实测 realtime 稳定性不达标时复议。
- **2026-08-12 决策 C（音质天花板）**：44.1kHz/16bit/立体声 ALAC，落定。调研结论：Apple 自家发送端抓包中 stream SETUP 无 `sr` 字段（隐含 44100）`[文档: airplay2-internals/index_rtsp.html]`；无任何实现/资料支持发送端 48k 或 24bit；Apple 官方 24/48 无损仅限 HomePod 本体播放 Apple Music，与 AirPlay 发送无关 `[文档: support.apple.com 118295]`。音质预算改投：高质量重采样（rubato）、位深转换抖动、虚拟声卡二次 SRC 排查（阶段二）。
- **2026-08-12 决策 D（虚拟音频设备策略）**：采纳 D1——不自研驱动，依赖第三方虚拟声卡；软件枚举渲染端点+引导用户选择，WASAPI loopback 采集。理由：Windows 11 驱动签名门槛（EV 证书+attestation）与 KISS/稳定性目标冲突。用户环境已安装 Steam Streaming Speakers，但**不预设选用**；阶段二须对候选虚拟声卡做音质调研（原生格式/位深、驱动二次 SRC、环路延迟）后定推荐。
- **2026-08-12 决策 E（配对与认证范围）**：用户 HomePod 访问控制为"所有人/同一网络中的任何人" → transient 配对（PIN 3939）可行。**仅支持无密码/无认证路线**：不实现 digest auth、不实现 HAP 持久配对（PIN 路径）；receiver 返回 401/403/470 时给出明确可操作的错误提示（指引用户修改 AirPlay 访问设置），不静默失败。
- **2026-08-12 决策 C 修订（用户批准）**：默认 44.1kHz/16bit/立体声保底；架构预留格式协商（明文 GET /info 探测设备能力），hi-res（48/16/2=0x100000、44.1/24/2=0x80000、48/24/2=0x200000）仅在设备广告支持时启用，真机验证。依据：airplay-cli 代码实现并声称验证 hi-res realtime `[代码: airplay-cli/src/ap2_client.c:1320-1329]`；MA README 称 24bit 自动启用于广告设备；反例教训"SETUP 200≠有声"→ 按设备广告启用 `[文档: airplay-cli/DESIGN.md §11]`。
- **2026-08-12 决策 E 修订（用户批准）**：首版仅 transient（PIN 3939）无密码路线；**HAP PIN pair-setup + pair-verify + 凭证持久化降级为已批准应急预案，触发条件=真机 transient 失败**。依据：后向兼容论证（transient 是十年存量设备连陌生 HomePod 的唯一机制，苹果不可能移除）；airplay-cli "transient 无声"实测可用单方实现 bug 解释（M4 后多发 M5→TLV error；密钥错→加密无声）`[假设]`。配套：首版诊断做足（配对每步结果/TLV 错误内容/SETUP 响应全文/RTP 发送计数入日志），确保一次真机测试即可远程判定失败点。
- **2026-08-12 实施默认项（用户批准）**：
  1. **里程碑切分**：① 探针 CLI（枚举声卡 + HomePod /info）→ ② 可播放 CLI（配对+推流，用户测试节点）→ ③ 托盘 GUI；
  2. **hi-res 启用顺序**：即使探针显示 HomePod 广告 hi-res，首版仍先 44.1/16/2 建立基线，稳定后经配置开 hi-res 试；
  3. **延迟窗口默认**：latencyMin=11025 / latencyMax=88200（250ms~2s，Apple/owntone 惯例）；降档风险自负（<500ms Wi-Fi 下实测"机器人化"）；
  4. **发现双通道**：mDNS 发现 + 手动 IP 输入保底；
  5. **v1 不做**：元数据/now-playing、多声道、MediaRemote、设备密码、PTP（触发条件=真机证明 NTP 不可行）、PIN pair-setup（触发条件=真机证明 transient 不可行）；
  6. **断流恢复**：keepalive miss×3 或 RTP 错误 → 新连接重配（每次配对新 socket）→ 自动恢复推流，指数退避；全程静音续传（splice 纪律）；
  7. **交付形态**：单 exe 便携版 + 日志文件（机器可读状态行 + 详细 tracing）；用户反馈=日志。
