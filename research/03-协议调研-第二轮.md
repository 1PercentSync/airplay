## 1. 第四独立实现 airplay-cli 的架构事实

- 单二进制：RAOP（libraop）+ AP2 RAOP-compat（auth-setup）+ AP2 native（HAP transient 或 pair-verify）`[文档: airplay-cli/DESIGN.md §3]`。
- Native 连接序：TCP → **GET /info（明文）** → HAP 配对 → 加密 RTSP（帧格式同前：`[2B LE][ct+16B tag]` ≤1024B，nonce=4零+8B LE 方向计数器）→ 计时建立 → session SETUP → eventPort 反向连接 → **RECORD → stream SETUP** →（PTP 会话）SETPEERS `[文档: DESIGN.md §3]`。
- GET /info 顺序存在两种可行变体：airplay-cli 明文先于配对 `[文档: DESIGN.md §3]`；FXChainPlayer 配对加密后 `[代码: raop_sender.cpp:1620-1624]`。实现时任选，建议 airplay-cli 顺序（/info 可在配对前用于能力探测）。
- stream SETUP 响应**必须按键名解析 plist**，不能按位置（接收端常把 controlPort 序列化在 dataPort 前，按位置解析会把音频发到控制口→无声）`[文档: DESIGN.md §3]`。
- 路由自动选择（mDNS TXT）：features bit38/48 → AP2；bit46/48 → 可配对；bit41 → PTP；bit40 → buffered；flags 0x8=需 PIN、0x200=legacy 配对；pw=true=需密码 `[文档: DESIGN.md §2；代码: src/ap2_client.c:1255-1295]`。
- 发现层：浏览 `_airplay._tcp` + `_raop._tcp`；`model=AudioAccessory*` → HomePod `[代码: AirSend/crates/airplay-core/src/discovery.rs:11-40]`。

## 2. 稳定性工程清单（第 1 优先级直接相关，全部来自实测）

1. **保活双机制最终定论**：`/feedback` 每 ~2s **且**服务加密事件通道（解密 `POST /command` 回最简 200 OK：仅 Server+可选 CSeq，无 `Content-Length: 0`/`Audio-Latency`）。pyatv 两者都做 `[代码: airplayv2.py:25,86-108,163-180]`；owntone 两者都做 `[代码: airplay_events.c:216-227]`；airplay-cli：`/feedback` ~2s + "The worker services encrypted reverse events after each feedback POST" `[文档: DESIGN.md §10]`；airplay2-rs 只做 feedback（缺陷实锤）。
2. **keepalive 容错**：超时形 miss 容忍连续 3 次（第 3 次判死），硬错误（reset/EOF/协议错）立即判死；迟到的响应按 CSeq 跳过、半截响应字节结转下一交换以保住 nonce 序列 `[文档: DESIGN.md §10]`。
3. **RTSP 串行化与 deadline**：一把互斥锁串行加密通道；分请求类型 deadline（feedback/控制 2s、元数据 5s、artwork 15s）；锁等待也计入 deadline `[文档: DESIGN.md §10]`。
4. **farewell TEARDOWN**：放弃通道前最后写一个 TEARDOWN（250ms 预算），否则接收端会话挂着反复爆音 `[文档: DESIGN.md §10]`。
5. **配对重试用新连接**：被拒的接收端在该 socket 上状态机卡死，每条配对腿必须新连接 `[文档: DESIGN.md §3a]`。
6. **splice timeline（对 Apple 接收端强制性）**：tvOS/**audioOS**(HomePod)/macOS 在任何缓冲丢弃（FLUSH）、锚定重宣告、队列 underrun 时发出 ~100ms 噪声（Apple TV 4K tvOS 27 实测 A/B）→ **实现纪律：锚定线一次冻结全程不变；间隙用编码静音作为普通块填平；队列永不干涸（空转/暂停时继续发静音）；flush 语义改为"停发+静音续传"而非丢弃** `[文档: DESIGN.md §10]`。
7. **接收端缓冲窗 ~2s**（latencyMax 88200 惯例）；接收端不回显时 pacing 回退 1.75s `[文档: DESIGN.md §11]`。

## 3. 协议细节修正与补充

- **音频密钥真正规则**：`cipher key == stream SETUP plist 中的 shk`，值本身任意——pyatv 用 HKDF(Events-Salt, Events-Write) 派生也能工作 `[代码: airplayv2.py:119-127]`；owntone/airplay-cli 惯例=共享秘密前 32B `[代码: ap2_hap.c:1186-1190]`。采用 owntone 惯例。
- **RTP 加密 nonce 两种变体均验证可行**：8B LE 独立计数器（pyatv/FXChainPlayer）vs RTP 序列号置于 offset 4（owntone/airplay-cli）；尾部 8B nonce 必须附加。AAD=RTP 头 [4..12) 一致。
- **SSRC 规则**：PTP 会话 SSRC=0（流以 PTP 钟标识）；NTP 会话 SSRC=streamConnectionID `[文档: DESIGN.md §7]`。
- **sync 包节奏 ~1s** `[代码: pyatv stream_client.py:133]`；首包 0x90 后续 0x80 `[代码: owntone airplay.c:2184-2195]`。
- **音量**：-30..0 dB 线性，0 → -144 静音哨兵，`SET_PARAMETER volume:` 三实现一致 `[代码: raop_sender.cpp:429-445; 文档: DESIGN.md §7]`。
- **RECORD 在 stream SETUP 之前**（Apple 顺序）：Samsung 接收端不这样就无声；Apple/Sonos 无回归 `[文档: DESIGN.md §11]`。
- **ct=1 裸 PCM 在 Apple TV 可行**（pyatv `audioFormat=0x800`），shairport-sync 作为接收端却硬编码 ALAC——"接收端硬编码 ALAC"仅对 shairport-sync 成立，Apple 接收端实际接受多种 ct；**但 HomePod 无 PCM 证据，维持 ALAC 路线** `[代码: airplayv2.py:133-135; shairport-sync/rtsp.c:2862]`。
- **B 决策获最硬证据**：airplay-cli 曾端到端实现 buffered (type 103) 并在 Sonos Era 100 验证后**删除**——Apple TV 对 buffered 流不发 Delay_Req 永不锚定；realtime 可承载一切；冷启动更慢 `[文档: DESIGN.md §9]`。
- **MediaRemote/MRP**：仅 Apple TV 的屏显 now-playing 需要；HomePod 音频不需要 → 不实现（KISS）`[文档: DESIGN.md §8]`。
- **PTP 实操细节**（推迟后参照）：接收端只接受 gPTP（majorSdoId=1）且只跟随 timing-peer 列表中的钟；sender 必须持 grandmaster `[文档: DESIGN.md §4,§11]`。airplay-cli 在 Apple TV 4K (tvOS 27) 以 PTP 运行。

## 4. 冲击已冻结决策的两个新证据（需用户复议）

### 4.1 决策 C（音质天花板）——发现 hi-res 资料

- airplay-cli **代码实现**四种 ALAC realtime 格式：`0x40000`=44.1/16/2、`0x100000`=48/16/2、`0x80000`=44.1/24/2、`0x200000`=48/24/2 `[代码: src/ap2_client.c:1320-1329; 文档: DESIGN.md §7]`，声称"16- and 24-bit ALAC render on the realtime stream on every tested receiver class" `[文档: DESIGN.md §9,§10]`。
- MA README：24-bit (44.1/48kHz) 播放**自动启用于广告 24-bit ALAC 的接收端** `[文档: ma_airplay_provider_README.md:13]`。
- 接收端能力信号：mDNS features bits 18-21 = AudioFormats_0..3 `[文档: airplay2-internals/index_features.html]`；`/info` 含 realtime/bufferStream 格式表 `[文档: DESIGN.md §9]`。
- 反例警告：设备格式表可能**低报**（Apple TV 实际能播 24bit 但不广告）；SETUP 200 可能**高报**（Sonos 48/24 返回 200 但无声）→ 策略应为"按设备广告启用 + opt-in" `[文档: DESIGN.md §11]`。
- **48/16 的额外价值**：可全链路 48kHz 直通（Windows 共享模式默认 48k），**消灭重采样环节**——比 44.1k 完美重采样更优。
- 待定：HomePod gen 2 实际广告/接受什么格式，只能真机探测（`/info` 明文可查，无需配对）。

### 4.2 决策 E（配对范围）——transient on HomePod 证据冲突

| 来源 | 声称 | 性质 |
|---|---|---|
| AirSend + airplay2-rs | HomePod gen 2 transient（PIN 3939，M4 止）有声，实测 | 单设备实测 `[代码: connection.rs:236-293; pair_setup.rs:66]` |
| airplay2-sender-cpp | HapTransient 标注"HomePod / AP2" | 声称 `[代码: raop_sender.cpp:1082-1087]` |
| **airplay-cli §11** | **"Apple TV/HomePod require stored credentials from a PIN pair-setup (transient returns 200 + an in-band TLV error and silence)"** | 舰队实测 `[文档: DESIGN.md §11]` |
| MA 用户文档 | HomePod 设"同一网络中的任何人"即可用（未要求配对） | 用户文档 `[文档: music-assistant.io]` |

- 冲突无法纸面解决（可能变量：固件版本/机型/访问控制档位/测量误差）。用户 HomePod 为 27.0，正落在 airplay-cli 声称"transient 无声"的版本区间（tvOS/audioOS 27 实测）。
- 工程正解（两家共同姿势）：**transient 先行（零 UX 成本），TLV error/无声则回退完整 HAP PIN pair-setup（M1-M6）+ 凭证持久化 + pair-verify**；FXChainPlayer 470 回退与 airplay-cli --auth 路径均为先例。
- 与原决策 E 的关系：设备**密码**路线维持不支持（airplay-cli 亦证实 AP2 密码无共识机制 `[文档: DESIGN.md §3a]`）；PIN pair-setup 是配对身份凭证，不是设备密码，属不同轴。
- HomePod PIN 呈现方式待查（无屏；可能 Siri 播报/家庭 App 显示——未验证）。
