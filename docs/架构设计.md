## 1. 设计原则

1. 优先级执行：稳定性 > 音质 > 延迟（需求 §4），所有取舍按此排序裁决；
2. 规范驱动：协议行为以 `docs/协议实现规范.md`（特性矩阵）为规范，引用处标注证据；
3. 白名单依赖（`research/05`），小而封闭组件自实现；
4. 每个字节的协议构造都可解释、可日志化——用户无法联调，日志是唯一的眼睛；
5. KISS：v1 不做清单（决策记录·实施默认项第 5 条）严格执行。

## 3. 线程/任务模型

| 执行体 | 类型 | 职责 | 实时约束 |
|---|---|---|---|
| 采集线程 | OS 线程 + MMCSS "Pro Audio" | WASAPI 事件驱动采集 f32 → SPSC 环 | 禁分配/锁；discontinuity 计数 |
| 音频加工任务 | tokio blocking 任务 | 环 → rubato → 44.1k → TPDF → 16bit → 352 帧块 → 有界 channel（64 块≈510ms） | 块不足不等待（发送侧静音纪律兜底） |
| 发送泵 | tokio 任务 | 墙钟令牌桶 44100/s；取块→ALAC→RTP→加密→UDP；**块不足发静音块**；维护重传 backlog 环 | pacing 误差 <1ms 目标 |
| 控制口任务 | tokio 任务（UDP） | 收 type 0x55 重传请求 → 0xD6 补发；收其他控制包记日志 | — |
| 计时任务 | tokio 任务（UDP） | NTP timing server（0xD3 应答）；1s 周期 sync（0xD4） | — |
| RTSP 会话任务 | tokio 任务 | 状态机（§4）；RTSP 串行化 + 分级 deadline；2s /feedback + 事件通道服务；keepalive miss 计数 | 通道死=终止（nonce 不重用） |
| mDNS 任务 | tokio 任务 | 浏览 `_airplay._tcp`/`_raop._tcp` | — |
| 控制面 | tokio 任务 | CLI 命令（start/stop/volume）、状态输出 | — |

## 4. 会话状态机

```
Idle → Probing(/info) → Pairing(M1→M2→M3→M4) → ChannelEncrypted
→ SetupSession → EventChannelOpen → RecordSent → StreamSetup
→ Streaming ⇄ Recovering(新连接重配,指数退避) → Teardown → Idle
```

硬性纪律（性质：自定纪律，见规范 §13；历史依据 `research/archive/03 §2`）：

1. 配对/重连一律**新 TCP 连接**（被拒的 socket 状态机卡死）；
2. RTSP 一把互斥锁串行化；deadline 分级：feedback/控制 2s、元数据 5s、SETUP 10s；锁等待计入 deadline；
3. keepalive 超时 miss 容忍连续 3 次（第 3 次判死），硬错误（reset/EOF）立死；迟到响应按 CSeq 跳过、半截字节结转至下一交换（保 nonce 序列）；
4. 判死时若最后请求完整发出 → farewell TEARDOWN（250ms 预算）；
5. 事件通道全程服务：解密 `POST /command` → 最简 200 OK（仅 Server + CSeq，禁多余头）；
6. 每步配对/SETUP 的请求摘要与响应全文（含 TLV/plist）写入日志。

## 5. 音频管线（音质纪律）

```
WASAPI loopback(f32, GetMixFormat 原生速率) → SPSC 环(256ms)
→ rubato sinc(48k→44.1k, sinc128/Blackman2/Quadratic；hi-res 协商成功则直通 48k)
→ TPDF 抖动量化(16bit；hi-res 24bit 时截 s32→packed s24)
→ 352 帧块 → [发送泵: ALAC 位写器 → RTP(12B 头) → ChaCha20-Poly1305(AAD=头[4..12], nonce 尾随 8B)] → UDP
```

- 设备混音格式 ≠48k 时：按原生速率采集，rubato 直接从原生速率→目标速率（不经过 48k 中转）；
- 采集零拷贝原则：GetBuffer 指针直接写入 SPSC 环；
- 打包队列满 → 丢**最旧**块并计数（新音频优先，配合静音纪律接收端无爆音——丢弃会制造间隙由发送泵静音填平）；
  > 注：丢块策略与静音纪律的交互在实现期用 mock receiver 验证（间隙必须被静音块精确填平，时间线不得跳变）。

## 6. 稳定性纪律（splice）

1. 时间线锚点一次冻结（首次 start_streaming 建立），全程不变；
2. **发送队列永不干涸**：无音频块时按 pacing 发送 ALAC 编码静音块（序列号/时间戳正常推进）；
3. 暂停（用户 stop→未来 pause）= 继续发静音，不发 FLUSH、不发 TEARDOWN；
4. 停止 =  farewell TEARDOWN 后关 socket（干净路径）；
5. 断流恢复：判死 → 指数退避（1s/2s/4s，封顶 30s）→ 全新连接重配 → 从当前墙钟恢复时间线（新锚点，旧会话已被接收端放弃）；恢复期间本地采集继续，块缓冲封顶。

## 7. 缓冲与延迟预算（默认档）

| 环节 | 值 | 备注 |
|---|---|---|
| WASAPI 事件周期 | ~10ms（设备默认） | 采集环 256ms 容错 |
| 打包队列 | 64 块 ≈ 510ms @44.1k | 背压缓冲 |
| 协商窗口 | latencyMin 11025 / latencyMax 88200（250ms~2s） | Apple/owntone 惯例 |
| 发送泵突发 | 每 tick ≤8 包（~64ms 音频）catch-up 上限 | 防 LAN 洪泛 |
| sync 节奏 | 1s | pyatv/owntone 一致 |
| 端到端延迟预期 | ~0.5-2.5s（接收端窗口决定） | 配置可降，风险自负 |

## 8. 诊断契约

- **状态行**（stdout + 日志文件，机器可读）：`[STATUS] probing|paired|setup_ok|streaming|recovering(n)|dead(reason)` 与计数器行 `[STATS] cap_disc=... q_drop=... rtx=... ka_miss=... reconnect=... rtp_sent=...`（每 10s）；
- **详细日志**（tracing，文件滚动）：配对每步 TLV 摘要、SETUP 请求/响应 plist 全文、/info 全文、错误链；
- 目标：用户跑一次 + 发日志 = 我能远程判定失败点（决策 E 修订配套要求）。

## 11. 风险与应急预案对应表

| 风险 | 触发证据 | 预案 |
|---|---|---|
| transient 被 HomePod 拒 | 真机：TLV error / 配对后无声 | 决策 E 预案：HAP PIN pair-setup + pair-verify + 凭证持久化（参照：pyatv auth/hap.py、owntone pair_homekit.c） |
| NTP 计时被拒 | 真机：SETUP 超时/无声且 RTP 计数正常 | 上 PTP（届时以 owntone PTP 会话代码为准） |
| Steam 声卡格式异常 | probe devices 输出 | 引导用户装 VB-CABLE（内部 SR=48000） |
| 48k/24bit 无声 | 真机（SETUP 200≠有声教训） | 回 44.1/16/2；格式协商仅按设备广告启用 |
| WASAPI 采集抖动 | 诊断计数异常 | MMCSS 已就位；增大采集环；采集线程优先级 |

## 12. 里程碑

1. **probe**：`probe devices` / `probe airplay <ip>`（明文 /info）/ `probe pair <ip>`（transient M1-M4 演练——最大风险点提前暴露，不出声）；
2. **run**：完整采集+推流（**用户测试节点**）；
3. **GUI**：托盘化 + 设备选择 + 状态显示。
